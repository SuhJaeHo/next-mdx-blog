### 실시간 오더북 렌더링 최적화 및 애니메이션 안정화

웹소켓 실시간 수신 데이터의 트래픽이 증가하면서 상태 갱신과 렌더링이 과도하게 발생하여 프레임 드롭이 생겼습니다. 이를 해결하기 위해 수신 데이터에 버퍼링과 500ms 단위의 배치 업데이트를 적용해 상태 갱신 횟수를 줄였고, 극한의 트래픽 상황을 가정한 스트레스 봇 테스트에서도 실시간 데이터 업데이트를 유지하면서 끊김 없이 서비스를 이용할 수 있었습니다.

또한 Page Visibility API로 탭 비활성화를 감지하여 웹소켓 연결을 해제하고, 탭이 다시 활성화되면 재연결 하도록 구현하였습니다. 백그라운드에 있는 동안 데이터가 버퍼에 쌓였다가 복귀 시점에 한 번에 처리되면서 프레임 드롭이 간헐적으로 발생하였는데, 웹소켓 연결 후 첫 수신 데이터가 최신 스냅샷 전체 데이터로 들어오는 구조였기 때문에 연결을 끊어 불필요한 버퍼 축적을 방지하고 복귀 시 재연결하는 방식으로 해결하였습니다.

각 오더북 행의 key에는 호가 값을 사용해, 정렬 순서가 변경되거나 해당 호가의 주문 수량이 갱신되더라도 동일한 호가의 컴포넌트 인스턴스가 유지되도록 구성했습니다. 이를 통해 이전 주문 수량과 현재 주문 수량을 비교해 변경 여부를 감지하고, 별도의 상태값 없이 블링크 애니메이션을 실행할 수 있었습니다.

블링크 애니메이션은 CSS Transition 대신 Framer Motion을 사용해 구현하였습니다. 호가창처럼 주문 수량이 짧은 간격으로 연속해서 변경되는 경우, CSS 상태 변경에 의존하는 방식은 진행 중인 애니메이션을 원하는 시점에 중단하고 처음부터 다시 시작하도록 제어하기가 까다로웠습니다. 그래서 Framer Motion을 사용해 애니메이션의 실행 상태를 직접 관리했습니다. 새로운 주문 수량이 들어오면 진행 중인 블링크 애니메이션을 즉시 중단하고, 초기화한 뒤 처음부터 재생하도록 처리하였습니다.

### RN WebView Bridge의 비동기 API 추상화

React Native WebView 환경에서는 WebView와 React Native 앱 간 메세지 기반 Bridge를 통해 요청을 전달하고, 처리 결과는 메세지 이벤트를 통해 비동기적으로 수신하는 구조였습니다. 이 때문에 요청 코드와 응답 처리 코드가 분리되어 있어, 호출한 곳에서 응답값을 직접 받아 후속 로직을 이어가거나 일반적인 비동기 API처럼 요청 상태를 관리하기 어려웠습니다.

이를 개선하기 위해 WebView-Native 간 Bridge 통신을 Promise를 반환하는 공통 함수로 추상화하였습니다. 메세지별 요청 파라미터와 응답 형식을 타입으로 정의하고, 요청 시 메세지 id를 기준으로 Promise의 resolve를 저장하였습니다. 이후 응답이 도착하면 공통 이벤트 핸들러에서 응답 id에 대응하는 Promise의 resolve를 찾아 호출하도록 구성해, 메세지 기반 Bridge 통신을 일반적인 비동기 API처럼 사용할 수 있도록 하였습니다.

이를 통해 호출부에서는 내부의 메세지 처리 방식을 알 필요 없이 응답값을 받아 후속 로직을 처리할 수 있었고, TanStack Query의 queryFn과 연결해 Bridge 통신도 서버 API와 유사한 방식으로 로딩·에러·응답 데이터를 관리할 수 있었습니다.

<CaseCodeDetails>
  <summary><span>Bridge 요청·응답의 Promise 변환</span></summary>

```tsx
type RNBridgeMessageMap = {
  "get-is-use-biometric": {
    params: null;
    response: BridgeResponse;
  };
};

const pendingRequestsRef = useRef<
  Record<
    keyof RNBridgeMessageMap,
    {
      resolve: (response: BridgeResponse) => void;
      reject: (error: unknown) => void;
    }
  >
>({});

const callRN = useCallback(
  <K extends keyof RNBridgeMessageMap>(
    message: {
      id: K;
      params: RNBridgeMessageMap[K]["params"];
    }
  ): Promise<RNBridgeMessageMap[K]["response"]> => {
    return new Promise((resolve, reject) => {
      // 메세지 id와 해당 요청의 Promise를 연결
      pendingRequestsRef.current[message.id] = {
        resolve,
        reject,
      };

      window.ReactNativeWebView?.postMessage(
        JSON.stringify(message)
      );
    });
  },
  []
);

const handleMessage = useCallback((event: MessageEvent) => {
  const response = JSON.parse(event.data) as BridgeResponse;

  // Native 응답의 id로 대응되는 Promise 탐색
  const pendingRequest =
    pendingRequestsRef.current[response.id];

  if (!pendingRequest) return;

  pendingRequest.resolve(response);
  delete pendingRequestsRef.current[response.id];
}, []);
```

### 이벤트 위임 기반 햅틱 피드백 공통화

WebView에서 버튼마다 햅틱 처리를 직접 구현하면 UI 컴포넌트와 Native Bridge 호출 로직 간의 결합도가 높아지고, 동일한 이벤트 처리 코드가 반복되는 문제가 있었습니다. 이를 개선하기 위해 햅틱이 필요한 요소에는 data-haptic 속성만 선언하고, 공통 터치 이벤트 리스너를 등록하여 해당 속성을 기준으로 햅틱을 처리하는 이벤트 위임 구조로 변경했습니다.

공통 핸들러에서는 터치가 종료된 요소에서 data-haptic 속성을 탐색해 필요한 햅틱 타입을 확인하고 Native Bridge를 호출하도록 구성했습니다. 이를 통해 개별 컴포넌트에서는 Bridge 호출이나 이벤트 리스너를 직접 관리할 필요 없이 HTML 속성만으로 햅틱 동작을 선언할 수 있게 했으며, 동적으로 추가되는 요소에도 동일한 규칙을 적용할 수 있었습니다.

또한 터치 시작 시점의 좌표를 저장하고, 이동 과정에서 거리를 계산해 일정 임계값을 초과하면 스크롤 또는 드래그로 판단했습니다. 이 경우 터치가 종료되더라도 햅틱을 실행하지 않도록 하여 스크롤 과정에서 의도하지 않은 햅틱이 발생하는 것을 방지했습니다.

- 이벤트 위임과 data-haptic 속성을 활용해 Native Bridge 호출을 공통화하고, UI 컴포넌트와 햅틱 구현 로직의 결합도를 낮춤
- 터치 이동 임계값을 기준으로 탭과 스크롤·드래그를 구분하여 의도하지 않은 햅틱 실행 방지

<CaseCodeDetails>
  <summary>구현 코드</summary>

```tsx
export default function useHapticFeedback() {
  const { needHapticFeedback } = useRNBridgeFetchers();

  const startPositionRef = useRef<{ x: number; y: number } | null>(null);
  const isDraggingRef = useRef(false);

  useEffect(() => {
    const handleTouchStart = (event: TouchEvent) => {
      const touch = event.touches[0];
      if (!touch) return;

      startPositionRef.current = {
        x: touch.clientX,
        y: touch.clientY,
      };

      isDraggingRef.current = false;
    };

    const handleTouchMove = (event: TouchEvent) => {
      const startPosition = startPositionRef.current;
      const touch = event.touches[0];

      if (!startPosition || !touch) return;

      const dx = Math.abs(touch.clientX - startPosition.x);
      const dy = Math.abs(touch.clientY - startPosition.y);

      // 일정 거리 이상 이동하면 탭이 아닌 스크롤·드래그로 판단
      if (dx > 10 || dy > 10) {
        isDraggingRef.current = true;
      }
    };

    const handleTouchEnd = (event: TouchEvent) => {
      if (isDraggingRef.current) return;

      // 실제 터치된 요소 또는 상위 요소에서 햅틱 설정 탐색
      const element = (event.target as HTMLElement).closest<HTMLElement>(
        "[data-haptic]"
      );

      const type = element?.dataset.haptic as
        | HapticFeedbackTypes
        | undefined;

      if (!type) return;

      needHapticFeedback({ type });
    };

    document.addEventListener("touchstart", handleTouchStart, {
      capture: true,
    });
    document.addEventListener("touchmove", handleTouchMove, {
      capture: true,
    });
    document.addEventListener("touchend", handleTouchEnd, {
      capture: true,
    });

    return () => {
      document.removeEventListener("touchstart", handleTouchStart, true);
      document.removeEventListener("touchmove", handleTouchMove, true);
      document.removeEventListener("touchend", handleTouchEnd, true);
    };
  }, [needHapticFeedback]);
}
```

### WebView SPA의 스택형 화면 전환 및 뒤로가기 제어

WebView 기반 SPA에서 네이티브 앱과 유사한 화면 전환 경험을 제공하기 위해 여러 화면을 Drawer 형태로 쌓는 스택 구조를 구현하였습니다. 현재 Drawer의 드래그 진행률을 기준으로 이전 Drawer의 이동량도 함께 계산하고, 진행률에 easing을 적용해 이전 Drawer가 자연스럽게 밀려났다가 복귀하도록 구성하였습니다. 이를 통해 두 Drawer가 하나의 화면처럼 연결되는 자연스러운 전환 효과를 구현하였습니다.

단일 라우트 SPA에서는 Drawer를 열어도 URL이 변경되지 않아 Android 뒤로가기 버튼으로 열린 Drawer를 순서대로 닫을 수 없는 문제가 있었습니다. 이를 해결하기 위해 Drawer가 열릴 때 가상 히스토리 항목을 추가하고, 뒤로가기 시 가장 상단의 Drawer부터 닫히도록 처리했습니다. 이를 통해 실제 페이지를 이동하지 않고도 Android 뒤로가기와 Drawer 스택의 이동을 동기화했습니다.

```tsx
const PREV_DRAWER_OFFSET = 100;
const DURATION = 400;
const EASING = "cubic-bezier(0.22, 1, 0.36, 1)";

const easeOutCubic = (s: number) => 1 - Math.pow(1 - s, 3);

function animatePrevDrawer(
  element: HTMLDivElement,
  open: boolean | undefined
) {
  element.style.willChange = "transform";
  element.style.transition = "none";

  const initialTransform = open
    ? "translate3d(0px, 0, 0)"
    : `translate3d(${-PREV_DRAWER_OFFSET}px, 0, 0)`;

  element.style.transform = initialTransform;

  // iOS WebView에서 초기 위치가 먼저 반영된 뒤
  // transition이 시작되도록 적용 시점을 분리
  requestAnimationFrame(() => {
    requestAnimationFrame(() => {
      element.style.transition = `transform ${DURATION}ms ${EASING}`;

      const finalTransform = open
        ? `translate3d(${-PREV_DRAWER_OFFSET}px, 0, 0)`
        : "translate3d(0px, 0, 0)";

      element.style.transform = finalTransform;
    });
  });
}

function animatePrevDrawerWithDrag(
  element: HTMLDivElement,
  rafIdRef: React.RefObject<number | null>,
  percentage: number
) {
  element.style.willChange = "transform";
  element.style.transition = "none";

  // 현재 Drawer의 드래그 진행률로
  // 이전 Drawer의 이동 거리 계산
  const eased = easeOutCubic(percentage);
  const x =
    -PREV_DRAWER_OFFSET + eased * PREV_DRAWER_OFFSET;

  rafIdRef.current = requestAnimationFrame(() => {
    element.style.transform = `translate3d(${x}px, 0, 0)`;
  });
}

export default function AnimatedDrawer({
  children,
  open,
  ...props
}: React.ComponentProps<typeof Drawer>) {
  const rafIdRef = React.useRef<number | null>(null);
  const isDraggedRef = React.useRef(false);

  const handleDrag = (_: unknown, percentage: number) => {
    isDraggedRef.current = true;

    const prevDrawer = getPrevDrawer();
    const currentDrawer = getCurrentDrawer();

    if (!prevDrawer || shouldSkipAnimation(currentDrawer)) {
      return;
    }

    // 이전 프레임을 취소하고
    // 가장 최근 드래그 위치만 반영
    if (rafIdRef.current) {
      cancelAnimationFrame(rafIdRef.current);
      rafIdRef.current = null;
    }

    animatePrevDrawerWithDrag(
      prevDrawer,
      rafIdRef,
      percentage
    );
  };

  return (
    <Drawer
      data-vaul-drawer
      {...props}
      open={open}
      onDrag={handleDrag}
    >
      {children}
    </Drawer>
  );
}
```

화면을 공통 Pull-To-Refresh 컴포넌트로 감싸기만 하면 별도의 구현 없이 iOS 네이티브처럼 화면을 아래로 당기는 인터랙션을 적용할 수 있도록 구성했습니다. 내부에 스크롤 영역이 있는 화면에서는 스크롤이 최상단일 때만 당김 동작을 시작해 제스처가 충돌하지 않도록 했고, 당긴 거리에 따라 저항이 점점 커지도록 처리해 자연스러운 움직임을 구현했습니다. 새로고침이 필요한 화면에서는 기준 지점을 넘었을 때 햅틱과 Rive Indicator를 실행한 뒤 비동기 작업을 수행하고, 완료되면 화면을 원래 위치로 복귀하도록 구성했습니다.
