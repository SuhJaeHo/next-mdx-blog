### リアルタイムオーダーブック描画の最適化とアニメーション安定化

WebSocketのリアルタイム受信トラフィックが増加し、状態更新とレンダリングが過剰に発生してフレームドロップが生じました。これを解決するため、受信データにバッファリングと500ms単位のバッチ更新を適用して状態更新の回数を減らし、極端なトラフィックを想定したストレスボットテストでもリアルタイムのデータ更新を維持しながら途切れなくサービスを利用できるようにしました。

また、Page Visibility APIでタブの非アクティブ化を検知してWebSocket接続を切断し、タブが再びアクティブになると再接続するように実装しました。バックグラウンドにいる間にデータがバッファに溜まり、復帰時に一括で処理されることで間欠的にフレームドロップが発生していましたが、WebSocket接続後の最初の受信データが常に最新スナップショット全体として届く構造だったため、接続を切断して不要なバッファの蓄積を防ぎ、復帰時に再接続する方式で解決しました。

各オーダーブック行のkeyには気配値を使用し、並び替えが発生した場合やその気配値の注文数量が更新された場合でも、同じ気配値のコンポーネントインスタンスが維持されるように構成しました。これにより、以前の注文数量と現在の注文数量を比較して変更の有無を検知し、別途状態を持たずにブリンクアニメーションを実行できました。

ブリンクアニメーションはCSS Transitionの代わりにFramer Motionを使って実装しました。オーダーブックのように注文数量が短い間隔で連続して変わる場合、CSSの状態変更に依存する方式では、進行中のアニメーションを狙ったタイミングで止めて最初からやり直すよう制御するのが難しくなります。そこでFramer Motionを使ってアニメーションの実行状態を直接管理しました。新しい注文数量が届くと、進行中のブリンクアニメーションを即座に停止し、初期化したうえで最初から再生するようにしました。

### RN WebView Bridgeの非同期API抽象化

React Native WebView環境では、WebViewとReact Nativeアプリ間でメッセージベースのBridgeを介してリクエストを伝え、処理結果はメッセージイベントを通じて非同期に受信する構造でした。そのためリクエストコードと応答処理コードが分離しており、呼び出し元で応答値を直接受け取って後続の処理につなげたり、一般的な非同期APIのようにリクエスト状態を管理することが難しくなっていました。

これを改善するため、WebView-Native間のBridge通信をPromiseを返す共通関数として抽象化しました。メッセージごとのリクエストパラメータと応答形式を型として定義し、リクエスト時にメッセージidを基準にPromiseのresolveを保存しました。その後応答が届くと、共通イベントハンドラーで応答idに対応するPromiseのresolveを探して呼び出すように構成し、メッセージベースのBridge通信を一般的な非同期APIのように使えるようにしました。

これにより呼び出し側では内部のメッセージ処理方式を知る必要なく応答値を受け取って後続の処理を行えるようになり、TanStack QueryのqueryFnと連携してBridge通信もサーバーAPIと同様の方法でローディング・エラー・応答データを管理できるようになりました。

```tsx
type RNBridgeMessageMap = {
  "get-is-use-biometric": {
    params: null;
    response: BridgeResponse;
  };
};

const pendingRequestsRef = useRef<
  Record<
    keyof RNBridgeMessageMap,
    {
      resolve: (response: BridgeResponse) => void;
      reject: (error: unknown) => void;
    }
  >
>({});

const callRN = useCallback(
  <K extends keyof RNBridgeMessageMap>(
    message: {
      id: K;
      params: RNBridgeMessageMap[K]["params"];
    }
  ): Promise<RNBridgeMessageMap[K]["response"]> => {
    return new Promise((resolve, reject) => {
      // メッセージidと該当リクエストのPromiseを紐付け
      pendingRequestsRef.current[message.id] = {
        resolve,
        reject,
      };

      window.ReactNativeWebView?.postMessage(
        JSON.stringify(message)
      );
    });
  },
  []
);

const handleMessage = useCallback((event: MessageEvent) => {
  const response = JSON.parse(event.data) as BridgeResponse;

  // Native応答のidに対応するPromiseを探索
  const pendingRequest =
    pendingRequestsRef.current[response.id];

  if (!pendingRequest) return;

  pendingRequest.resolve(response);
  delete pendingRequestsRef.current[response.id];
}, []);
```

### イベント委譲によるハプティックフィードバックの共通化

WebViewでボタンごとにハプティック処理を直接実装すると、UIコンポーネントとNative Bridge呼び出しロジックの結合度が高まり、同じイベント処理コードが繰り返される問題がありました。これを改善するため、ハプティックが必要な要素にはdata-haptic属性のみを宣言し、共通のタッチイベントリスナーを登録して該当属性を基準にハプティックを処理するイベント委譲構造に変更しました。

共通ハンドラーでは、タッチが終了した要素からdata-haptic属性を探索して必要なハプティックタイプを確認し、Native Bridgeを呼び出すように構成しました。これにより各コンポーネントではBridge呼び出しやイベントリスナーを直接管理する必要なく、HTML属性だけでハプティック動作を宣言できるようになり、動的に追加される要素にも同じルールを適用できました。

また、タッチ開始時点の座標を保存し、移動過程で距離を計算して一定のしきい値を超えるとスクロールまたはドラッグと判定しました。この場合はタッチが終了してもハプティックを実行しないようにし、スクロール中に意図しないハプティックが発生することを防ぎました。

- イベント委譲とdata-haptic属性を活用してNative Bridge呼び出しを共通化し、UIコンポーネントとハプティック実装ロジックの結合度を低減
- タッチ移動のしきい値を基準にタップとスクロール・ドラッグを区別し、意図しないハプティック実行を防止

<CaseCodeDetails>
  <summary>実装コード</summary>

```tsx
export default function useHapticFeedback() {
  const { needHapticFeedback } = useRNBridgeFetchers();

  const startPositionRef = useRef<{ x: number; y: number } | null>(null);
  const isDraggingRef = useRef(false);

  useEffect(() => {
    const handleTouchStart = (event: TouchEvent) => {
      const touch = event.touches[0];
      if (!touch) return;

      startPositionRef.current = {
        x: touch.clientX,
        y: touch.clientY,
      };

      isDraggingRef.current = false;
    };

    const handleTouchMove = (event: TouchEvent) => {
      const startPosition = startPositionRef.current;
      const touch = event.touches[0];

      if (!startPosition || !touch) return;

      const dx = Math.abs(touch.clientX - startPosition.x);
      const dy = Math.abs(touch.clientY - startPosition.y);

      // 一定距離以上移動した場合はタップではなくスクロール・ドラッグと判定
      if (dx > 10 || dy > 10) {
        isDraggingRef.current = true;
      }
    };

    const handleTouchEnd = (event: TouchEvent) => {
      if (isDraggingRef.current) return;

      // 実際にタッチされた要素、またはその上位要素からハプティック設定を探索
      const element = (event.target as HTMLElement).closest<HTMLElement>(
        "[data-haptic]"
      );

      const type = element?.dataset.haptic as
        | HapticFeedbackTypes
        | undefined;

      if (!type) return;

      needHapticFeedback({ type });
    };

    document.addEventListener("touchstart", handleTouchStart, {
      capture: true,
    });
    document.addEventListener("touchmove", handleTouchMove, {
      capture: true,
    });
    document.addEventListener("touchend", handleTouchEnd, {
      capture: true,
    });

    return () => {
      document.removeEventListener("touchstart", handleTouchStart, true);
      document.removeEventListener("touchmove", handleTouchMove, true);
      document.removeEventListener("touchend", handleTouchEnd, true);
    };
  }, [needHapticFeedback]);
}
```

### WebView SPAのスタック型画面遷移と戻る操作の制御

WebViewベースのSPAでネイティブアプリに近い画面遷移体験を提供するため、複数の画面をDrawer形式で積み重ねるスタック構造を実装しました。現在のDrawerのドラッグ進行率を基準に前のDrawerの移動量も一緒に計算し、進行率にeasingを適用して前のDrawerが自然に押し出されてから戻るように構成しました。これにより、二つのDrawerが一つの画面のようにつながる自然な遷移効果を実現しました。

単一ルートのSPAではDrawerを開いてもURLが変わらないため、Androidの戻るボタンで開いているDrawerを順番に閉じることができない問題がありました。これを解決するため、Drawerが開く際に仮想の履歴項目を追加し、戻る操作時に最も上にあるDrawerから閉じるように処理しました。これにより、実際のページ遷移を伴わずにAndroidの戻る操作とDrawerスタックの移動を同期させました。

```tsx
const PREV_DRAWER_OFFSET = 100;
const DURATION = 400;
const EASING = "cubic-bezier(0.22, 1, 0.36, 1)";

const easeOutCubic = (s: number) => 1 - Math.pow(1 - s, 3);

function animatePrevDrawer(
  element: HTMLDivElement,
  open: boolean | undefined
) {
  element.style.willChange = "transform";
  element.style.transition = "none";

  const initialTransform = open
    ? "translate3d(0px, 0, 0)"
    : `translate3d(${-PREV_DRAWER_OFFSET}px, 0, 0)`;

  element.style.transform = initialTransform;

  // iOS WebViewで初期位置が先に反映されてから
  // transitionが始まるようにタイミングを分離
  requestAnimationFrame(() => {
    requestAnimationFrame(() => {
      element.style.transition = `transform ${DURATION}ms ${EASING}`;

      const finalTransform = open
        ? `translate3d(${-PREV_DRAWER_OFFSET}px, 0, 0)`
        : "translate3d(0px, 0, 0)";

      element.style.transform = finalTransform;
    });
  });
}

function animatePrevDrawerWithDrag(
  element: HTMLDivElement,
  rafIdRef: React.RefObject<number | null>,
  percentage: number
) {
  element.style.willChange = "transform";
  element.style.transition = "none";

  // 現在のDrawerのドラッグ進行率から
  // 前のDrawerの移動距離を計算
  const eased = easeOutCubic(percentage);
  const x =
    -PREV_DRAWER_OFFSET + eased * PREV_DRAWER_OFFSET;

  rafIdRef.current = requestAnimationFrame(() => {
    element.style.transform = `translate3d(${x}px, 0, 0)`;
  });
}

export default function AnimatedDrawer({
  children,
  open,
  ...props
}: React.ComponentProps<typeof Drawer>) {
  const rafIdRef = React.useRef<number | null>(null);
  const isDraggedRef = React.useRef(false);

  const handleDrag = (_: unknown, percentage: number) => {
    isDraggedRef.current = true;

    const prevDrawer = getPrevDrawer();
    const currentDrawer = getCurrentDrawer();

    if (!prevDrawer || shouldSkipAnimation(currentDrawer)) {
      return;
    }

    // 直前のフレームをキャンセルし、
    // 最新のドラッグ位置だけを反映
    if (rafIdRef.current) {
      cancelAnimationFrame(rafIdRef.current);
      rafIdRef.current = null;
    }

    animatePrevDrawerWithDrag(
      prevDrawer,
      rafIdRef,
      percentage
    );
  };

  return (
    <Drawer
      data-vaul-drawer
      {...props}
      open={open}
      onDrag={handleDrag}
    >
      {children}
    </Drawer>
  );
}
```

### ネストスクロールを考慮したPull-to-Refresh

画面を共通のPull-to-Refreshコンポーネントで包むだけで、個別の実装なしにiOSネイティブのように画面を下に引くインタラクションを適用できるように構成しました。内部にスクロール領域がある画面ではスクロールが最上部にあるときだけ引く動作を開始するようにしてジェスチャーが競合しないようにし、引いた距離に応じて抵抗が徐々に強くなるように処理して自然な動きを実現しました。更新が必要な画面では、基準地点を超えた時点でハプティックとRive Indicatorを実行した後に非同期処理を行い、完了すると画面を元の位置へ復帰させるように構成しました。
