### Optimizing Real-Time Order Book Rendering and Animation Stability

As WebSocket traffic increased, excessive state updates and rendering caused frame drops. To resolve this, I applied buffering and 500ms batch updates to the incoming data to reduce the number of state updates, and even under a stress-bot test simulating extreme traffic, the service kept receiving real-time updates without interruption.

I also used the Page Visibility API to detect tab inactivity, close the WebSocket connection, and reconnect once the tab became active again. While in the background, data kept accumulating in the buffer and was processed all at once on return, which intermittently caused frame drops. Since the first message after reconnecting always arrived as a full latest snapshot, I closed the connection to prevent unnecessary buffer buildup and simply reconnected on return, which resolved the issue.

I used the quote price as the key for each order book row so that the same quote's component instance stays the same even when the sort order changes or the order quantity at that quote is updated. This let me detect changes by comparing the previous and current order quantity, and implement the blink animation without any separate state.

The blink animation is implemented with Framer Motion instead of CSS Transition. In an order book, where order quantities change repeatedly in quick succession, relying on CSS state changes made it hard to stop a running animation at the right moment and restart it cleanly from the beginning. So I used Framer Motion to manage the animation's execution state directly. When a new order quantity comes in, the running blink animation is stopped immediately, reset, and replayed from the start.

### Abstracting the RN WebView Bridge into an Async API

In the React Native WebView environment, requests were passed through a message-based Bridge between the WebView and the React Native app, with responses arriving asynchronously through message events. This meant request code and response-handling code were separated, making it hard for callers to receive a response value directly and continue their logic, or to manage request state the way a normal async API would.

To improve this, I abstracted the WebView-Native Bridge communication into a shared function that returns a Promise. I defined the request parameters and response shape per message as types, and stored the Promise's resolve keyed by a message id at request time. When the native app's response arrived, a shared event handler looked up the resolve matching the response id and called it, making the message-based Bridge communication usable like a normal async API.

This let callers receive the response value and continue their logic without needing to know the internal messaging mechanism, and by wiring it into TanStack Query's queryFn, Bridge calls could be managed with the same loading, error, and response handling as a server API.

<CaseCodeDetails>
  <summary><span>Converting Bridge Requests and Responses to Promises</span></summary>

```tsx
type RNBridgeMessageMap = {
  "get-is-use-biometric": {
    params: null;
    response: BridgeResponse;
  };
};

const pendingRequestsRef = useRef<
  Record<
    keyof RNBridgeMessageMap,
    {
      resolve: (response: BridgeResponse) => void;
      reject: (error: unknown) => void;
    }
  >
>({});

const callRN = useCallback(
  <K extends keyof RNBridgeMessageMap>(
    message: {
      id: K;
      params: RNBridgeMessageMap[K]["params"];
    }
  ): Promise<RNBridgeMessageMap[K]["response"]> => {
    return new Promise((resolve, reject) => {
      // Link the message id to this request's Promise
      pendingRequestsRef.current[message.id] = {
        resolve,
        reject,
      };

      window.ReactNativeWebView?.postMessage(
        JSON.stringify(message)
      );
    });
  },
  []
);

const handleMessage = useCallback((event: MessageEvent) => {
  const response = JSON.parse(event.data) as BridgeResponse;

  // Find the Promise matching the native response's id
  const pendingRequest =
    pendingRequestsRef.current[response.id];

  if (!pendingRequest) return;

  pendingRequest.resolve(response);
  delete pendingRequestsRef.current[response.id];
}, []);
```

### Unifying Haptic Feedback with Event Delegation

Implementing haptic handling directly on every button in the WebView tightly coupled UI components to how the Native Bridge was called, and repeated the same event-handling code across components. To improve this, I declared a data-haptic attribute on any element that needed haptics and moved to an event-delegation structure with a shared touch event listener that reads that attribute.

The shared handler looks up the data-haptic attribute on the element where the touch ended to determine the haptic type, then calls the Native Bridge. This let individual components declare haptic behavior with just an HTML attribute, without managing Bridge calls or event listeners directly, and the same rule applied automatically to dynamically added elements.

I also stored the touch start coordinates and, as the touch moved, calculated the distance to decide whether it had become a scroll or drag once it crossed a threshold. In that case, haptics were skipped even if the touch ended, preventing unintended haptics during scrolling.

- Used event delegation and the data-haptic attribute to unify Native Bridge calls and reduce the coupling between UI components and haptic logic
- Distinguished taps from scroll/drag using a touch-movement threshold to prevent unintended haptic feedback

<CaseCodeDetails>
  <summary>Implementation</summary>

```tsx
export default function useHapticFeedback() {
  const { needHapticFeedback } = useRNBridgeFetchers();

  const startPositionRef = useRef<{ x: number; y: number } | null>(null);
  const isDraggingRef = useRef(false);

  useEffect(() => {
    const handleTouchStart = (event: TouchEvent) => {
      const touch = event.touches[0];
      if (!touch) return;

      startPositionRef.current = {
        x: touch.clientX,
        y: touch.clientY,
      };

      isDraggingRef.current = false;
    };

    const handleTouchMove = (event: TouchEvent) => {
      const startPosition = startPositionRef.current;
      const touch = event.touches[0];

      if (!startPosition || !touch) return;

      const dx = Math.abs(touch.clientX - startPosition.x);
      const dy = Math.abs(touch.clientY - startPosition.y);

      // Treat movement past a threshold as a scroll/drag, not a tap
      if (dx > 10 || dy > 10) {
        isDraggingRef.current = true;
      }
    };

    const handleTouchEnd = (event: TouchEvent) => {
      if (isDraggingRef.current) return;

      // Look up haptic config on the touched element or its ancestor
      const element = (event.target as HTMLElement).closest<HTMLElement>(
        "[data-haptic]"
      );

      const type = element?.dataset.haptic as
        | HapticFeedbackTypes
        | undefined;

      if (!type) return;

      needHapticFeedback({ type });
    };

    document.addEventListener("touchstart", handleTouchStart, {
      capture: true,
    });
    document.addEventListener("touchmove", handleTouchMove, {
      capture: true,
    });
    document.addEventListener("touchend", handleTouchEnd, {
      capture: true,
    });

    return () => {
      document.removeEventListener("touchstart", handleTouchStart, true);
      document.removeEventListener("touchmove", handleTouchMove, true);
      document.removeEventListener("touchend", handleTouchEnd, true);
    };
  }, [needHapticFeedback]);
}
```

### Stacked Screen Transitions and Back Navigation in a WebView SPA

To give a WebView-based SPA a screen-transition experience close to a native app, I implemented a stack structure that piles multiple screens as Drawers. I calculate the previous Drawer's movement from the active Drawer's drag progress and apply easing so the previous Drawer is pushed out naturally and eases back in. This makes the two Drawers feel connected, as if they were a single screen transitioning together.

Because opening a Drawer doesn't change the URL in a single-route SPA, the Android back button couldn't close open Drawers in order. To fix this, I push a virtual history entry each time a Drawer opens and close the topmost Drawer first on back navigation. This synchronizes the Android back gesture with the Drawer stack without any actual page navigation.

const PREV_DRAWER_OFFSET = 100;
const DURATION = 400;
const EASING = "cubic-bezier(0.22, 1, 0.36, 1)";

const easeOutCubic = (s: number) => 1 - Math.pow(1 - s, 3);

function animatePrevDrawer(
  element: HTMLDivElement,
  open: boolean | undefined
) {
  element.style.willChange = "transform";
  element.style.transition = "none";

  const initialTransform = open
    ? "translate3d(0px, 0, 0)"
    : `translate3d(${-PREV_DRAWER_OFFSET}px, 0, 0)`;

  element.style.transform = initialTransform;

  // Split the timing so the initial position is painted on iOS WebView
  // before the transition starts
  requestAnimationFrame(() => {
    requestAnimationFrame(() => {
      element.style.transition = `transform ${DURATION}ms ${EASING}`;

      const finalTransform = open
        ? `translate3d(${-PREV_DRAWER_OFFSET}px, 0, 0)`
        : "translate3d(0px, 0, 0)";

      element.style.transform = finalTransform;
    });
  });
}

function animatePrevDrawerWithDrag(
  element: HTMLDivElement,
  rafIdRef: React.RefObject<number | null>,
  percentage: number
) {
  element.style.willChange = "transform";
  element.style.transition = "none";

  // Derive the previous Drawer's offset from the active Drawer's
  // drag progress
  const eased = easeOutCubic(percentage);
  const x =
    -PREV_DRAWER_OFFSET + eased * PREV_DRAWER_OFFSET;

  rafIdRef.current = requestAnimationFrame(() => {
    element.style.transform = `translate3d(${x}px, 0, 0)`;
  });
}

export default function AnimatedDrawer({
  children,
  open,
  ...props
}: React.ComponentProps<typeof Drawer>) {
  const rafIdRef = React.useRef<number | null>(null);
  const isDraggedRef = React.useRef(false);

  const handleDrag = (_: unknown, percentage: number) => {
    isDraggedRef.current = true;

    const prevDrawer = getPrevDrawer();
    const currentDrawer = getCurrentDrawer();

    if (!prevDrawer || shouldSkipAnimation(currentDrawer)) {
      return;
    }

    // Cancel the pending frame and apply only the latest
    // drag position
    if (rafIdRef.current) {
      cancelAnimationFrame(rafIdRef.current);
      rafIdRef.current = null;
    }

    animatePrevDrawerWithDrag(
      prevDrawer,
      rafIdRef,
      percentage
    );
  };

  return (
    <Drawer
      data-vaul-drawer
      {...props}
      open={open}
      onDrag={handleDrag}
    >
      {children}
    </Drawer>
  );
}

### Pull-to-Refresh for nested scrolling

Wrapping a screen in a shared Pull-to-Refresh component applies an iOS-native-style pull-down interaction without any per-screen implementation. On screens with an inner scroll area, the pull gesture only starts when that scroll is at the top, so it never conflicts with normal scrolling, and resistance increases gradually with pull distance for a natural feel. On screens that need a refresh, crossing the threshold triggers haptics and the Rive indicator before running the async task, and the screen returns to its original position once it completes.
