<div className="case-solution-block">

### Abstracting RN WebView Bridge Communication into a Promise-Based API

I abstracted React Native WebView's message-based Bridge communication into a shared Promise-based API so callers could use it the same way as a normal asynchronous API.

- The existing Bridge separated request sending from response event handling, making it difficult for the caller to receive a response value directly, continue follow-up logic, or manage request state.
- I abstracted Bridge requests into a shared function that returns a Promise and defined each message's request parameters and response shape with TypeScript types.
- I stored each Promise's resolve by the generated message id at request time, then used a shared event handler to find and execute the matching resolve when a response arrived.
- This let callers use the Bridge like a normal await-based async API without knowing the internal postMessage and event-handling structure.
- I connected the shared Bridge function to TanStack Query's queryFn so native communication could manage loading, error, and response data state the same way as server APIs.

<div className="case-tags"><span>React Native WebView</span><span>TypeScript</span><span>Promise</span><span>TanStack Query</span></div>

</div>

<CaseCodeDetails>
  <summary><span>Converting Bridge Requests and Responses to Promises</span></summary>

```tsx
type RNBridgeMessageMap = {
  "get-is-use-biometric": {
    params: null;
    response: BridgeResponse;
  };
};

const pendingRequestsRef = useRef<
  Record<
    keyof RNBridgeMessageMap,
    {
      resolve: (response: BridgeResponse) => void;
      reject: (error: unknown) => void;
    }
  >
>({});

const callRN = useCallback(
  <K extends keyof RNBridgeMessageMap>(
    message: {
      id: K;
      params: RNBridgeMessageMap[K]["params"];
    }
  ): Promise<RNBridgeMessageMap[K]["response"]> => {
    return new Promise((resolve, reject) => {
      // Link the message id to this request's Promise
      pendingRequestsRef.current[message.id] = {
        resolve,
        reject,
      };

      window.ReactNativeWebView?.postMessage(
        JSON.stringify(message)
      );
    });
  },
  []
);

const handleMessage = useCallback((event: MessageEvent) => {
  const response = JSON.parse(event.data) as BridgeResponse;

  // Find the Promise matching the native response's id
  const pendingRequest =
    pendingRequestsRef.current[response.id];

  if (!pendingRequest) return;

  pendingRequest.resolve(response);
  delete pendingRequestsRef.current[response.id];
}, []);
```

</CaseCodeDetails>

### Unifying Haptic Feedback with Event Delegation

Implementing haptic handling directly on every button in the WebView tightly coupled UI components to Native Bridge calls and repeated the same event-handling code across components.

- I changed the structure so elements that need haptics only declare a data-haptic attribute, and a shared touch event listener handles haptics through event delegation based on that attribute.
- The shared handler searches for the data-haptic attribute from the element where the touch ended, determines the required haptic type, and calls the Native Bridge.
- This let individual components declare haptic behavior with only an HTML attribute, without directly managing Bridge calls or event listeners, and the same rule also applied to dynamically added elements.
- I stored the coordinates at touch start and calculated movement distance so movement over a threshold was treated as scroll or drag.
- When the interaction was judged as scroll or drag, haptics were skipped even on touch end, preventing unintended haptic feedback during scrolling.

### Stack-Based Screen Transitions and Back Navigation in a WebView SPA

To provide a native-app-like screen transition experience in a WebView-based SPA, I implemented a stack structure where multiple screens are layered as Drawers.

- Based on the current Drawer's drag progress, I also calculated the previous Drawer's offset and applied easing to the progress so the previous Drawer is pushed away and returns naturally.
- This made the two Drawers feel connected as one continuous screen transition instead of moving independently.
- In a single-route SPA, opening a Drawer does not change the URL, so the Android back button could not close open Drawers in stack order.
- To solve this, I added a virtual history entry when a Drawer opens and handled back navigation so the topmost Drawer closes first.
- This synchronized Android back navigation with the Drawer stack state without actual page navigation.
